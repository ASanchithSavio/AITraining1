# Video Games prompt review gates

Use these gates with the general method. Exact game titles, prototype names, switch locations, signal names, pin numbers, URLs, and manual outcomes remain in ignored local notes.

## Domain and version control

- Keep the task anchored in a released game, its documented prototype, hardware, software, cabinet, service history, or contemporary coverage.
- Freeze the platform, region, cabinet style, board revision, manual printing, and service-note date whenever any of them can change the answer.
- Do not treat a home-console port, arcade release, conversion kit, sequel, and later reproduction board as interchangeable.
- Prefer completed historical releases and fixed documentation over live patches, current storefronts, rankings, or availability.

## Answer-first hardware design

- Select the terminal schematic cell, pin, connector, test signature, or parts-list entry before drafting clues.
- Render and inspect the decisive drawing. Record the sheet, circuit block, source designator, destination designator, signal label, and every adjacent pin or line.
- Ask for a directly printed identifier. Do not require electrical calculation, reverse engineering from an emulator, or inference from an unofficial PCB recreation.
- Preserve a meaningful distinction between switch number, board location, buffer input, buffer output, bus line, and processor pin.

## Source graph

- A useful chain can join an archival prototype title to the released game, use a contemporary maintenance record to select a control or component, and then carry that selection through a manufacturer schematic.
- Require at least two substantive decisions after the released title is known. Game identification alone is not a durable difficulty mechanism.
- Make each source necessary. Remove an archive, magazine, manual, or schematic when its output is not consumed by the next hop.
- Use independent publication ecosystems when the benchmark requires them. Several mirrors of one operator manual remain one underlying source.

## Schematic and scan controls

- Treat page OCR as discovery only. Verify traces, row alignment, pin numbers, active-low bars, and split-sheet continuity from the rendered image.
- Check whether a large schematic sheet was scanned as two physical PDF pages. State both the printed sheet identifier and the physical PDF page in private evidence.
- Follow named nets across schematic blocks; do not assume that a switch number equals a data-bit number or an IC pin.
- Record plausible wrong answers from the same trace, especially the buffer input pin, buffer output pin, adjacent data bit, and sound-processor pin.

## Shortcut, wording, and promotion gates

- Search the prototype alias with the maintenance symptom, the released title with the selected control or component, and the proposed terminal vocabulary.
- Reject a candidate when a repair log, emulator source, forum post, or indexed OCR snippet exposes the full location-to-answer join.
- State upstream identity facts naturally. Do not narrate the archive, maintenance note, schematic, and manual as a browsing itinerary.
- Repeat `released game`, `selected option switch`, `buffered data line`, and `main processor` when a pronoun could attach to multiple devices.
- A candidate that passes these checks is ready for one fresh user-run target-model test; it is not yet an empirical model failure.
- A correct terminal answer retires the architecture regardless of elapsed time.
